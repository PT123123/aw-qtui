# 配对按钮按需显示修改计划

> 状态：已实施（2026-09-07，Debug 构建通过）。目标：发起配对按钮和接受配对按钮不再一直显示在设备上，而是探测到可以发起或接受配对时，才在对应设备上显示。

## 1. 问题诊断

当前实现中，`buildUi()` 在设备 tab 内创建了一个独立的"配对"分组（`QGroupBox`），其中始终显示"发起配对"和"接受配对"两个按钮：

```cpp
// src/syncpage.cpp buildUi() ~L150
auto *pairBox = new QGroupBox(QStringLiteral("配对"));
auto *pl = new QHBoxLayout(pairBox);
m_btnInitiatePair = new QPushButton(QStringLiteral("发起配对"));
connect(m_btnInitiatePair, &QPushButton::clicked, this, &SyncPage::onInitiatePair);
m_btnAcceptPair = new QPushButton(QStringLiteral("接受配对"));
connect(m_btnAcceptPair, &QPushButton::clicked, this, &SyncPage::onAcceptPair);
pl->addWidget(m_btnInitiatePair);
pl->addWidget(m_btnAcceptPair);
pl->addStretch(1);
devLay->addWidget(pairBox);
```

问题：
- **发起配对**按钮：无论是否有未配对的远端设备可见，始终显示。
- **接受配对**按钮：无论是否有远端设备发来配对请求，始终显示。

这会让用户误以为随时可以操作，而实际上按钮仅在特定设备状态下才可用。

## 2. 修改方案

### 2.1 核心思路

将配对按钮从独立的"配对"分组移到设备列表（`m_devTable`）中，作为行内操作列：
- **发起配对**按钮：仅出现在 `paired == false && !isSelf && discovery == true`（已广播发现但尚未配对）的设备行。
- **接受配对**按钮：仅出现在存在 `pair_request` 待处理状态的设备行（服务端在设备 JSON 中返回 `pending_request: true` 之类的字段，或通过日志判断是否有本端 `pair/accept` 可响应的请求）。

如果服务端当前不返回 `pending_request` 字段，则先以"已广播发现但未配对的设备"作为"可发起配对"的判断依据；"接受配对"按钮在探测到对方发来的配对请求时出现。

### 2.2 UI 调整

1. **删除固定"配对"分组**：移除 `pairBox`、`pairBox` 布局及相关提示文字。
2. **设备表新增一列"操作"**：在现有 7 列之后新增第 8 列，表头显示"操作"。
3. **按设备状态注入按钮**：在 `refreshDevices()` 的填充循环中，对每行设备按需创建按钮：
   - 若 `!d.paired && !d.isSelf && d.discoverable`（可被发现但未配对）→ 放"发起配对"按钮。
   - 若 `d.pairRequestPending`（远端发来了配对请求，本机可接受）→ 放"接受配对"按钮。
   - 否则该格留空。

### 2.3 代码改动清单

| 文件 | 改动 |
|------|------|
| `src/syncpage.h` | 删除 `QPushButton *m_btnInitiatePair`、`QPushButton *m_btnAcceptPair` 成员变量（或保留但不再在 buildUi 中固定创建） |
| `src/syncpage.cpp` `buildUi()` | 删除固定 `pairBox` 及按钮创建逻辑；在 `m_devTable` 表头加入"操作"列 |
| `src/syncpage.cpp` `refreshDevices()` | 在行循环中按设备状态按需创建并放置"发起配对"或"接受配对"按钮到操作列 |
| `src/models.h` | 若服务端可返回 `pending_request` 字段，给 `SyncDevice` 加 `bool pairRequestPending` 成员与反序列化 |
| `src/syncpage.cpp` `onInitiatePair()` / `onAcceptPair()` | 从当前行的设备 ID 获取目标（不再依赖全局"当前选中行"，改用按钮 `sender()` 的 `property`） |

### 2.4 按钮点击事件绑定

不再依赖全局 `m_devTable->currentRow()`，改为：
```cpp
auto *btn = qobject_cast<QPushButton*>(sender());
const QString devId = btn->property("deviceId").toString();
```

这样用户无需先"选中行"，直接点击行内按钮即可。

## 3. 探测逻辑

### 3.1 可发起配对
条件：
- `!d.isSelf`（非本机）
- `!d.d.paired`（未配对）
- 该设备通过 UDP 广播或静态 IP 被发现（已在 `m_devices` 列表中）

### 3.2 可接受配对
条件（需服务端支持）：
- 远端设备已向本机发来配对请求
- 服务端在 GET /devices 返回的设备 JSON 中包含 `pending_request: true`（或类似字段）
- 或者本机日志中可见 `pair_request_received` 事件（降级方案：仅当日志中出现时显示）

> 注：`pending_request` 字段需由 aw-server-rust 侧确认是否已有或需新增。若尚未支持，则先实现"发起配对"按设备出现，"接受配对"按钮暂保持隐藏或留 TODO。

## 4. 风险与回滚

- 删除固定分组可能影响已习惯操作流程的用户 → 在文档中说明。
- `SyncDevice` 新增字段需要后端配合 → 若后端暂不支持，先软判断（日志检测）。
- 操作列按钮动态创建需要刷新后生效，不影响已有定时刷新逻辑。

## 5. 待确认

- aw-server-rust 是否已在 `GET /devices` 的返回 JSON 中包含"待接受配对请求"字段？
- 若需要新增字段，是否需同步修改 `apiclient.h` 的请求？
- "接受配对"在业务语义上是否仅对"远端发来的请求"触发，还是也包括本机收到广播后主动发起？

## 6. 实施顺序

1. 修改 `buildUi()`：移除固定配对分组，表头新增"操作"列。
2. 修改 `refreshDevices()`：按需在操作列放置按钮。
3. 修改 `onInitiatePair()` / `onAcceptPair()`：使用 `sender()` property 获取 deviceId。
4. 若需新增字段：扩展 `SyncDevice` 结构体、反序列化、ApiClient 文档。
5. 编译验证，观察设备列表刷新后按钮是否按预期出现/隐藏。
