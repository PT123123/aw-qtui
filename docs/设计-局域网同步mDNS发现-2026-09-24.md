# 局域网设备发现：mDNS 首选 + UDP 广播兜底

日期：2026-09-24
范围：`aw-server-plus/aw-sync-rust`（一份 Rust 同时服务桌面与 Android）、`aw-android-native`、`aw-qtui`
关联：[设计-局域网同步信封加密-2026-09-24](./设计-局域网同步信封加密-2026-09-24.md)（哈希别名与安全码在那一份里）

---

## 1. 要解决什么

改造前只有 UDP 定向广播一条路径，它的三个性质在真实网络里会咬人：

- **子网掩码是猜的**：广播地址由 `本机 IP | !255.255.255.0` 算出（`discovery.rs::subnet_broadcast`），
  换到 /22、访客网络、AP 隔离的网段就发不出去或发给自己。
- **可达信息全靠自报**：`ip`/`port` 是 JSON 里的自报字段，接收端还得用 UDP 源地址反过来纠正它
  （`listener_loop` 里那段 `is_usable_ip(&src_ip)` 逻辑就是为此）。DNS-SD 有标准承载位：
  地址进 A 记录、端口进 SRV 记录。
- **没有下线语义**：只能靠 HTTP 探活硬猜「这台还在不在」。mDNS 有标准的
  goodbye（`unregister` 时向链路发 TTL=0）与 cache-flush，上下线是事件而不是超时。

同时明确 mDNS 的坏处，这也是**不删掉 UDP 广播**的理由：

- 组播在部分 AP 上被吞（IGMP snooping / 「组播转单播」的商用 AP / 访客网络隔离），
  那种环境里广播反而是唯一能通的。
- Android 必须额外持 `MulticastLock` 才收得到组播（见 §5）。
- 5353 是众所周知的端口，防火墙与隔离策略更容易拦它。

所以结论不是「换成 mDNS」，而是**两条路径同时跑，靠来源仲裁决定谁的信息落库**。

## 2. 落到哪一层

实现放在 Rust 服务端（`aw-sync-rust/src/mdns.rs`，生成部分 322 行、另 83 行单测），不放客户端：

- 桌面（aw-qtui）与 Android 共用一份实现，不必各写一套 DNS-SD。
- 发现的产物是「本地信任列表里的设备记录」，那本来就是服务端 `sync.db` 的状态，
  放客户端还要把结果回灌给服务端。
- `aw-qtui` 里那套 Win32 `dnsapi.dll` 的 `MdnsDiscovery` 从头到尾没被启动过
  （`mainwindow.cpp:160` 只 `new` 出来，`startBrowse()` 无人调用），保留在树里只会误导。
  服务类型常量两边一致（`config.h:11` 与 `mdns.rs::SERVICE_TYPE` 都是
  `_activitywatch._tcp.local.`），因此真机上两端仍能互相发现——**待退役**（§9）。

依赖选 `mdns-sd` 0.21.4，`default-features = false`：纯 Rust、自带 mio 线程，
不引入第二套 async 运行时（与信封加密那一份同样照顾 Android 交叉编译）。

## 3. 宣告什么、不宣告什么

| 字段 | 取值 | 理由 |
| --- | --- | --- |
| 实例名 / host_name | `hashed_alias(device_id)`，8 位十六进制 | 主机名一旦进 A/SRV 记录就等于广播给整条链路；别名同时保证同一台设备在任何一侧看到的名字稳定 |
| TXT `v` | `"1"` | 版本不符的服务一律不认领 |
| TXT `id` | 真实设备 id | **归并主键**：实例名撞名被 DNS-SD 改名（`DnsNameChange`）也不影响识别 |
| TXT `kind` | `windows`/`android`/… | 列表图标，无需配对即可知 |
| 地址 / 端口 | A 记录 / SRV 记录 | 由 DNS 解析得出，不再依赖对端自报，也就省掉了「用 UDP 源地址反纠自报 IP」那一步 |

> 诚实的边界：SRV 只是给端口一个标准承载位。今天 `SyncManager::new`（`manager.rs:67`）会把
> `listen_port` 一律修正为实际服务端口 5600，两条路径报出的都是同一个值，
> 「改端口后对端连不上」这条限制**并未因本轮而解除**（要改的是那个修正逻辑，不是发现协议）。

真实设备名仍然只在配对后的 HTTP 报文里交换（`refresh_peer_from_handshake`），
与 UDP 广播的隐私姿态保持一致。

两处 `mdns-sd` 的坑记下来免得复发：

1. `host_name` **必须以 `.local.` 结尾**，否则 `register_service` 直接报
   `Hostname must end with '.local.'`——第一轮测试全零结果就是它。
2. 多网卡时地址集合是 `HashSet`，迭代顺序不稳定。`pick_ipv4` 过滤掉回环/未指定/链路本地
   之后**取数值最小者**，固定下来，否则同一台设备每轮换一个地址，日志里看不出连的哪块网卡。

daemon 还顺手 `disable_interface(IfKind::IPv6)` 与 `(IfKind::LoopbackV4)`：同步端点是 IPv4
的 HTTP，IPv6 地址只会让对端挑到连不通的那个。

## 4. 仲裁：谁是权威

两条路径共用**同一个入库入口** `discovery::record_peer(db, dev, via, note)`，
不允许各自写库。规则只有一条：

> 已有记录是 mDNS 报的、且那次解析仍在 `MDNS_FRESH_SECS = 45s` 之内，这次来自 UDP 广播 → 不改写 ip/port。

其余组合一律放行（新设备、老记录来源未知、mDNS 覆盖广播、广播之间互相覆盖）。
落败方仍然调用 `touch_seen`，所以「还活着」这件事两条路径都能维护。

新鲜期存在 `devices` 的两个新列里（`storage.rs::migrate` 用 `ensure_column` 补，老库无需迁移）：

- `seen_via`：`"mdns"` / `"udp"` / `NULL`（老数据、配对或手动登记）
- `seen_via_at`：**那次宣告真正落库的时刻**

`seen_via_at` 不能复用 `last_seen_at`：备选路径落败时也会刷 `last_seen_at`，
每 5 秒一次的广播会把 45 秒窗口无限续期，mDNS 真哑了之后 UDP 永远补不上去。
`losing_broadcast_does_not_extend_mdns_window` 专门钉住这一点。

mDNS 路径失败（daemon 起不来、注册报错）只降级不致命：UDP 广播照旧在跑。

## 5. Android：组播锁

Wi-Fi 芯片默认在省电状态过滤组播帧，系统只在应用持有 `WifiManager.MulticastLock` 时
才把组播投递上来。`CHANGE_WIFI_MULTICAST_STATE` 权限早就在清单里（`AndroidManifest.xml:18`）
但从未被使用—— UDP 广播是**广播**帧，不受组播过滤影响，所以老方案确实不需要它。

新增 `sync/MulticastLocks.kt`：按 owner 计数的共享锁（界面与后台自愈窗口是两个持有方，
最后一个释放才真正放下），生命周期与 Rust 侧发现开关严格对齐，**不常驻**（持锁会明显增加待机耗电）：

| 持有方 | acquire | release |
| --- | --- | --- |
| `sync-page` | `SyncFragment.onResume`（紧接 `startDiscovery()`） | `onPause`（`stopDiscovery()` 之后） |
| `lan-heal-window` | `LanSyncNetworkMonitor.rediscoverAndSyncNow`（重发现窗口） | `try/finally`，窗口结束即放 |

已知限制：Rust 内部自发的 burst（`spawn_auto_sync` 探测失败时自己开的那一轮）在 Kotlin 之外，
拿不到锁——那条路径在安卓上仍以 UDP 广播为主。

## 6. 配置词汇

`discovery_method` 的取值从「`broadcast` / `poll`」改成「`mdns`（默认）/ `udp_only` / `poll`」：

- 判定写成 `mdns_enabled = method != "udp_only"`（`manager.rs::ensure_discovery_threads`），
  于是**所有存量安装（老默认值 `broadcast`）自动获得 mDNS 首选**，不需要数据库迁移。
- `endpoints.rs::config_save` 桌面端「配置开启即恢复广播」的条件去掉了
  `== "broadcast"` 那半句——默认值一改它就永远不成立，`discovery_running` 会一直 false
  （第一轮 e2e 失败正是这个原因）。
- Android 设置页下拉按新词汇展示，老值归到第一档显示、下次保存自动改写；
  `aw-qtui` 保存配置时改写 `"mdns"`（原来硬编码 `"broadcast"`）。

## 7. 线程与门控

`ensure_discovery_threads` 一次拉起 4 条常驻线程，实际收发由进程级
`DISCOVERY_ACTIVE` 逐轮门控：

`aw-sync-announce` / `aw-sync-listen`（UDP 广播，原有）+
`aw-sync-mdns-announce` / `aw-sync-mdns-browse`（新增）。

桌面端 `discovery_persistent()` 为 true（发现常驻），Android 端仍只在同步界面可见时收发。

## 8. 验证

| 命令 | 结果 |
| --- | --- |
| `cargo test -p aw-sync-rust` | 50/50 绿（37 lib + 4 e2e + 8 pairing + 1 mDNS 双进程） |
| `cargo check --workspace` | exit 0，仅既有警告 |
| `gradlew :mobile:compileDebugKotlin --offline` | BUILD SUCCESSFUL；同一次构建里 `:mobile:cargoBuild` + `checkRequiredSoFiles` 通过，即 `mdns-sd` 的安卓交叉编译与 `.so` 产物成立 |
| `cargo test -p aw-sync-rust --test mdns_discovery -- --nocapture` | 真实局域网（`192.168.5.34`）双向发现，1.7s 内双方都落库，未走跳过分支 |

**测试台架的关键教训**：同进程模拟两台设备是假象。`mdns-sd` 的注册与浏览共用一个 daemon
套接字，自己发出的应答会被自己按「非外部来的包」处理掉，实测只能单向解析——修好
`host_name` 之后同进程用例仍只有 A→B 通、B→A 不通。所以 `tests/mdns_discovery.rs` 改成
**双进程**：`examples/mdns_node.rs`（`mdns_node <data_dir> <device_id> [secs]`）跑完整发现逻辑，
测试轮询各自 `sync.db` 里 `protocol=Mdns` 的入向日志，并断言地址取自 A 记录、端口取自 SRV、
`paired=false`、`name == hashed_alias(peer)`。诊断同一个工具也用于真机排障。

## 9. 未做 / 待办

- **真机手测**：桌面 ↔ 手机在同一个 Wi-Fi 下互相发现（重点看手机进同步页后能否被 mDNS 报到，
  以及离开页面后组播锁是否真的放下）；Windows 防火墙弹窗若拦 5353 需放行 UDP。
  本轮只有双进程 `mdns_node` 的实机证据（同一台机器两个进程，等同两台设备的网络关系）。
- `aw-qtui` 的死 mDNS 模块（`src/mdnsdiscovery.h/.cpp`、`mainwindow.cpp:160` 的 `m_mdns`）待退役，
  等确认真机上不再依赖它做兜底。
- 单播 DNS-SD / 跨 VLAN（走 mDNS 单播查询）未做；`poll`（轮询遍历）仍是占位。
- 同进程只能绑一次 UDP 46000 是既有约束（本机有真实 `aw-server.exe` 在跑时，
  测试进程的监听会 `os error 10048` 并 5 秒重试）；本轮没改。
- `storage.rs::touch_online` 用字符串比较 `last_seen_at > datetime('now','-30 seconds')`
  判在线，与 RFC3339（含 `T` 与时区偏移）不同格式，跨日会误判——既有缺陷，与本轮无关。
  **已在本轮同日跟进修掉**（改用 `last_seen_epoch` 整数比较），见
  [设计-设备身份归并-2026-09-24](./设计-设备身份归并-2026-09-24.md) §4。
