# 服务端源码共享目录方案（aw-server-plus）

> 落地日期：2026-09-24 · 影响仓库：`aw-qtui`、`aw-android-native`、`aw-server-plus`

## 背景

`aw-qtui` 与 `aw-android-native` 各自以 git submodule 形式挂了同一个 fork
`PT123123/aw-server-plus`：

| 位置 | pin 提交 | 源码 | target 缓存 |
| --- | --- | --- | --- |
| `aw-android-native/aw-server-rust` | `941c8c3`（2026-09-15，detached） | 1.3M | 4.2G |
| `aw-qtui/vendor/aw-server-rust` | `25f5fa4`（2026-09-19，main） | 1.3M | 3.7G |

两份 checkout 各 pin 在不同提交上，服务端改一次要在两处同步、两边分别构建；`941c8c3`
是 `25f5fa4` 的祖先，说明差异纯粹来自「两份副本更新节奏不同」而非有意的版本隔离。

## 决策

workspace 根只保留一份服务端源码，两个客户端仓库用 **junction** 指过去：

```
<workspace>/                              # 例：activitywatch 目录，两个客户端仓库与服务端源码同级
├── aw-server-plus/                       # 唯一源码（独立 git 仓库，main @ 25f5fa4，origin+upstream 保留）
│   └── target/                         # aw-android 交叉编译缓存（rust-android-gradle 硬编码 <module>/target）
├── aw-android-native/aw-server-rust    → junction → ..\aw-server-plus
└── aw-qtui/
    ├── vendor/aw-server-rust           → junction → ..\..\aw-server-plus
    └── .cargo-target-server/           # aw-qtui 私有 cargo 缓存（justfile 注入 CARGO_TARGET_DIR）
```

- **为什么用 junction 而不是改脚本路径**：`mobile/build.gradle` 的 `cargo { module = "../aw-server-rust" }`、
  `scripts/win/build.ps1`、`build_rust.cmd`、`build.gradle` 的 `excludeDirs` 全部按原路径生效，
  零改动即零踩坑；代价是这两个路径变成未跟踪目录，已分别写进各自 `.gitignore`。
- **为什么源码共享但 target 分开**：Android 侧注入 `RUSTFLAGS`（`debuginfo=2` + max-page-size）且
  target triple 不同，与 `aw-qtui` 本机 MSVC 构建共用一份缓存会让两边增量互相打回全量重编。
  `aw-qtui` 因此显式设 `CARGO_TARGET_DIR`；Android 侧无法设（Gradle 插件按 `<module>/target` 找 `.so`），
  所以 `<共享源码>/target` 归 Android 专用。

## 落地要点

1. 两边的 submodule 记录已解除：`git rm --cached` 掉 gitlink、`.gitmodules` 中对应段清空
   （`aw-qtui` 的 `.gitmodules` 已随之删除，`aw-android-native` 只剩 `media` 一个子模块）、
   `.git/config` 的 `[submodule ...]` 段移除。
2. 版本统一到 `25f5fa4`：`aw-android-native` 侧相当于向前 4 天的服务端提交。arm64 交叉编译已通过，
   但 APK 在真机上的行为（JNI 建桶 `!local` 展开、datastore v6 迁移）仍需回归一次。
3. `aw-qtui` 原工作树里两个未跟踪文件随迁移保留：`aw-server/windows/app.ico`（构建期产物）与
   `docs/d1-sync-recovery.md`（本地笔记），现在位于共享源码目录内、仍是 ignored 状态。
4. 更新服务端 = 在任一 junction 路径里 `git -C vendor/aw-server-rust pull --ff-only origin main`，
   两边同时生效；不再存在「两边 pin 不同步」这类冲突（参见
   [冲突记录 · D1 双端互覆](冲突记录-aw-server-rust-D1双端互覆-2026-09-05.md)）。

## 验证结论

路径级：`cargo metadata` 在两条 junction 路径下解析出的 `target_directory` 正确（qtui 走
`.cargo-target-server`，android 走 `<共享源码>/target`）；往共享目录写探针文件，两个链接同时可见
（实证同一棵树）；两边 `git submodule status` 不再含 `aw-server-rust`；junction 路径已被各自
`.gitignore` 忽略。

构建级：

- `just server`（aw-qtui）→ `Finished release profile in 1.99s`，**零 crate 重编**，
  `build/server/aw-server.exe` 正常部署 —— 缓存搬到 `.cargo-target-server/` 后完全没失效。
- `./gradlew :mobile:cargoBuildArm64`（aw-android-native）→ `BUILD SUCCESSFUL in 3m 17s`，
  新 `libaw_server.so` 写进 `aw-server-plus/target/aarch64-linux-android/release/` 并被复制到
  `mobile/build/rustJniLibs/android/`。日志里的路径形如
  `.../aw-android-native/aw-server-rust/target/...`，说明 cargo 用的就是 junction 路径本身、
  没被规范化成 `aw-server-plus`，因此跨仓库的缓存定位保持稳定。

## 遗留

- 旧副本移到 workspace 根的 `.quarantine-20260924/`（android 的 worktree 与 git dir，约 3.4M，无独有
  ref、无未提交改动），构建验证通过后由维护者手动删除：`Remove-Item -Recurse -Force .quarantine-20260924`。
- 回滚：在删除隔离目录之前，把两份复制回 `aw-android-native/aw-server-rust` 与
  `aw-qtui/.git/modules/vendor/aw-server-rust`，再 `git revert` 对应提交即可（本方案没有改动任何
  服务端源码内容）。
- 后续可选：`aw-server-plus/target/` 里若积累多个 target triple 的产物，可按需单独清理，但不要
  删 `.cargo-target-server/`（那是 Qt 侧的服务端增量缓存）。
