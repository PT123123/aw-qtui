# 局域网同步信封加密（B 方案）

日期：2026-09-24
范围：`aw-server-plus/aw-sync-rust`（一份 Rust 同时服务桌面与 Android）、`aw-qtui`、`aw-android-native`

---

## 1. 要解决什么

桌面端 `aw-server` 监听 `0.0.0.0:5600`，同步报文在局域网里是**明文 HTTP**。两类对手：

- **被动抓包**：同网段任意设备嗅探流量，就能读到 activity / inbox / todo 的全部内容和真实主机名。
- **主动读取**：直接 `GET /api/0/sync/devices`、`/config`（含 `d1_api_token`）、`/log`。

本轮只做**被动抓包**这一层（用户原话：B 方案「正好是你说的『轻微防范』」）。A 方案（配置级 `api_key` + Bearer）是地板不是答案，**未实施**——它不防被动抓包（key 就躺在 header 里），而且一旦开启会让局域网内的对端全部 401（`apikey.rs` 的 fairing 覆盖除 `/api/0/info` 外的所有 `/api/...` 路径），需要同步路由豁免才能上线。

结论：**传输仍走明文 HTTP，只把报文体加密**。

## 2. 信任根与威胁模型

配对成功那一刻，双方各生成随机 32 字节 `device_secret`，随 pair/confirm 报文交换一次。此后所有同步正文都是信封。

明确承认的弱点：**没有身份绑定**。配对那 5 分钟窗口里，同网段中间人可以把交换中的 `device_secret` 换走，之后两端各自以为自己在使用共享密钥。两个极便宜的缓解都已落地：

1. 配对码 `CODE_LEN` 从 4 位提到 **6 位**（`paircode.rs:14`），暴力命中概率压到可忽略；
2. 两端同步页各显示一个 **4 位十六进制「安全码」**（`crypto::fingerprint`，Signal 安全号码的做法），人工核对一致即说明中间没有第三人。**加指纹比加位数有效得多**。

## 3. 信封格式

实现在 `aw-sync-rust/src/crypto.rs`（405 行，含 9 个单元测试）。

```json
{ "v": 1, "kid": "<发送方设备 id>", "ts": 1777000000, "n": "<base64 12B nonce>", "ct": "<base64 密文||tag>" }
```

- **算法**：AES-256-GCM（`aes-gcm` 0.11，12 字节随机 nonce、16 字节标签拼在密文尾部）。
- **密钥派生**：HKDF-SHA256，`ikm=device_secret`、`salt="aw-sync/1"`、`info=接口路径`。
  按用途分子密钥——推送密钥（`/api/0/sync/push`）与拉取密钥（`/api/0/sync/snapshot`）互不相通，`wrong_secret_or_wrong_path_fails` 覆盖。
- **AAD**：`"aw-sync/1\n{path}\n{kid}\n{ts}"`。发送方身份、目标接口、时间戳全部绑进认证标签，改写 `kid` 换目标重放、篡改 `ts` 都会在 GCM 校验阶段直接失败（`tampered_ciphertext_and_kid_rejected`）。
- **防重放**：接收端在 ±300s 窗口内对 `(kid, nonce)` 去重（进程内 `HashMap`，超 4096 条按时间窗淘汰）。
- **入站健壮性**：局域网报文长度不受信，`nonce`/`ct` 先自行校验长度再构造 `Array`，避免 `Array::from_slice` panic。

### 策略：信封 ⟺ 有密钥

`seal_body` / `open_body` 把策略收在一处：

| 本机是否持有该对端密钥 | 出站 | 入站收到明文 | 入站收到信封 |
| --- | --- | --- | --- |
| 有 | 信封 | **拒收**（判定为降级攻击） | 解开，失败即报错 |
| 无（旧端 / 热点直连） | 明文 | 照旧可用 | 报错：没有密钥解不开 |

「已协商密钥却仍收到明文 → 拒收」是关键的单向门：否则中间人只要把密钥丢掉就能逼出明文。回滚窗口期要注意：解除配对会同时删密钥（见下），旧端不会被这道门永久卡住。

## 4. 密钥存储：绝不出接口

因为 `/api/0/sync/devices`、`/config`、`/log` 对局域网所有设备可读，密钥的存放方式按「结构性不可能泄漏」设计：

- 独立表 `device_secrets(device_id, secret, updated_at)`，**不**是 `devices` 表的一列；
- `models.rs` 上 `Device.device_secret` 只是**线上字段**：`row_to_device` 恒返回 `None`，`/join`、`/devices`、`add_device`、`self_device_info`、UDP 广播全部显式置 `None`；
- `serde(default)` + `skip_serializing_if`，旧版本收到带这个键的 JSON 不会被打挂（避免重演 `paired_at` 那次兼容事故）；
- 日志只写「密钥：随报文附带（日志不落密钥）」这类元信息；配对码数字也从日志里移除；
- 生命周期：`adopt_incoming_secret`（入站采纳，非法/缺失则本机新生成）→ `absorb_secret_from`（采纳对端响应回传的密钥，**以对端为准**，双方由此收敛到同一把，不需要额外往返）→ 重新配对即轮换；`delete_device` / `delete_all_devices` 连带删除密钥行（残留旧密钥会让后续合法明文被错误拒收）。
- 端到端断言：`sync_e2e_http.rs` 里 step 6.6 检查 `GET /devices` 原始响应体**不含** `device_secret` 字样。

## 5. UDP 广播的机器名泄漏

被动抓包最先看到的就是主机名。广播只承担「有人在这儿」+ 可达地址，因此（`discovery.rs:166`）：

- `announce.name` 换成 `hashed_alias(device_id)` = SHA-256(`"aw-sync/alias/1\n{id}"`) 前 8 位十六进制；
- 真实设备名在配对后的 HTTP 报文里才交换，`refresh_peer_from_handshake` 用它回填本地登记。

未做：给广播套同一信封（广播是单向宣告，没有配对前的共享密钥可用）。

## 6. 安全码怎么到 UI

`storage.rs::fingerprints(self_id)` 从 `device_secrets` 列出所有对端并算 `peer_id -> 4 位大写十六进制`（设备 id 按字典序归一，保证两端结果一致）。

- `GET /devices` 的每个设备对象附带 `encrypted: bool` 与 `fingerprint: string`（仅在有密钥时）。
- 配对/加入/确认的成功响应同样回传 `fingerprint`，所以**配对完成那一刻就能看到码**，不必等下次刷新。

### Qt（`aw-qtui`）

- `models.h`：`SyncDevice` 新增 `fingerprint` / `encrypted`。
- `syncpage.ui`：设备表新增第 9 列「安全码」，表头带 toolTip 说明核对意义。
- `syncpage.cpp::renderDevices`：本机显示 `—`；有指纹显示指纹；已配对但无密钥显示「未加密」。
- `onUsePairCode` 重写：先弹本机配对码，再从**未配对**设备里选目标（多于一个用 `QInputDialog::getItem` 选择器），调 `/join-remote`；成功日志把安全码打出来提醒核对。提示语刻意不写「6 位」，以免旧四位码对端被误认为不可用。

### Android（`aw-android-native`）

- `item_sync_device_paired.xml` + `SyncRowsAdapter.kt`：`lastSync` 下方一行 `安全码 XXXX（请与对端核对）`，无密钥的已配对设备显示「未加密（重新配对可启用加密同步）」。

## 7. 两处客户端接线的新接口

### `POST /join-remote`（修掉一个既有 bug）

Qt 原来的「使用配对码配对」把**对端的码**提交给了**本机** `/join`，而配对码只存在于创建方（码主）的 `sync.db` 里，所以这条路径永远返回「配对码无效」——码主永远收不到你。现在 `join_remote`（`manager.rs:723`）由本机按设备登记 ip:port 定向把码 POST 给**对端** `/join`，并吸收响应里的 `{device, peer, device_secret, fingerprint}`。请求体：`{device_id, code}`。

### `POST /push-to`（热点传输的回程推送）

WiFi 热点传输原先在 Kotlin 里手搓 HTTP：`GET 本机 /snapshot` → `POST 对端 /push`。加了降级拒绝之后这条路必然失败——**客户端拿不到密钥**（密钥按设计从不出服务端接口），只能发明文，而对端的 `/push` 拒收。

所以把导出 + 信封化 + 发送整体收回 Rust：

```jsonc
// 请求：{ "ip": "192.168.43.1", "port": 5600, "device_id": "...", "name": "..." }
// 响应：{ "applied": <合入条数>, "encrypted": true|false }
```

`device_id` 为空时回退成 `hotspot-<ip>` 且不带密钥（热点直连就是明文）。附带好处：多 MB 的 JSON 不再绕经 App 层往返一遍。

Kotlin 侧对应删除：`SyncApi.getSnapshot()`、`WifiHttp.postJson()`；`WifiTransferFragment` 的第 4–5 步合成一次 `localApi.pushTo(...)`，`encrypted` 为真时记一条「已用配对密钥加密推送」。

**热点「拉取」这一腿仍是明文**：`GET 对端 /snapshot` 由 Kotlin 直连，故意不带 `?from=`，对端按「无共享密钥」返回明文。要加密就得让服务端中转（同 `/push-to` 的思路，例如本机 `/pull-from`），本轮未做——热点场景下两端往往还没配对，收益有限。配对过的两台机器走局域网同步时，拉取是 `?from=<自己的 id>` → 信封（`encode_snapshot_body`，`manager.rs:271`）。

## 8. Rocket 体积上限

信封是 base64，体积膨胀约 4/3。Rocket 0.5 默认 `bytes` / `string` 上限 **8KiB**，而 `/push` 现在以原始字节接收正文（要先嗅探 `kid` 才能选密钥，不能用 `Json<T>` 直接反序列化），大快照会被直接 413。已在 `aw-server/src/config.rs:88` 把 `json` / `data-form` / `bytes` 提到 1000MB（桌面 `main.rs` 与 Android `android/mod.rs` 共用这段配置），测试的 figment 同步跟上。

1. 测试服务的 `listen_port` 仍是默认 5600 → UDP 广播把对端 ip:port 改写成**用户真机**的 `192.168.5.34:5600`，于是要么 500「拒收明文」要么连不通。现在 `spawn_server` 显式写入 `listen_port`/`udp_port`，不共享广播端口的用例各用 `free_udp_port()`。
2. 测试的 inbox fixture 落后于生产 schema（缺 `uuid` 等列）→ `no such column`。fixture 现在与 `aw-inbox-rust::migrate()` 对齐。

`pair_flow_initiate_accept_confirm` 新增 step 8 断言热点路径：`/push-to` 对已配对目标返回 `encrypted: true`，且笔记确实落到对端 inbox。

## 10. 未做 / 待办

- **真机手测**（本轮无自动化）：Qt 与 Android 的「安全码」列展示与两端一致性、6 位配对码对话框、热点传输走一遍加密路径。Android 侧需要先 `gradlew :mobile:cargoBuildArm64` 重打 `libaw_server.so`，本轮代码改动才进 APK。
