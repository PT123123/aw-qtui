# 内存占用分析与优化方案

> 结论日期：2026-09-18
> 适用版本：aw-qtui 0.1.10 / 0.1.11
> 关联机制：可淘汰页生命周期（懒建 + 离开即回收 + LRU 有界缓存）

## 一、背景问题

aw-qtui 运行时内存一度升到 **200 MB 以上**。最初怀疑是「数据存储的字符串占大头」或「渐变主题吃内存」。实测结果否定了这两个猜测：它们占比极小。

本文给出实测的内存构成，以及为压内存采取的优化方案。

## 二、内存占比实测结论

### 1. 先分清两个指标

| 指标 | 实测值（运行中） | 含义 |
|---|---|---|
| **工作集 Working Set** | ~188 MB | 进程驻留在 RAM 的所有页，**含与其它进程共享的代码** |
| **私有内存 Private** | ~115 MB | 真正属于 aw-qtui 自己的堆 |
| **已加载映像（代码）** | ~143 MB | 123 个 DLL/EXE 的映射大小 |

任务管理器默认显示的「内存」通常是**工作集**，它会计入大量**系统 DLL + Qt 运行库的共享代码页**（Qt6Gui/Qt6Widgets/Qt6Core 合计约 21 MB，另有 shell32、d2d1、d3d11 等系统库），这部分是每个进程的公共底盘，并非 aw-qtui 独有。

### 2. 逐项占比

| 组成 | 估算 | 说明 |
|---|---|---|
| 数据存储（字符串） | **~1–2 MB** | 实测客户端加载的本地文件合计仅 ~138 KB（inbox_local.json 128 KB + todo 5.8 KB + focus 3.9 KB），读进内存也就 1–2 MB |
| 渐变主题 | **< 1 MB** | 渐变仅是一个 `QLinearGradient` 画刷对象，按窗口存几条规则，不是按像素存的缓冲；100 MB 级别的猜想不成立 |
| 界面/控件/样式系统 | **几十 MB（本金大头）** | 启动时一次性 eager 构造了全部页面（收件箱 + 专注 8 页 + 活动 4 页 + 同步 4 页 + 设置），合计数百个 QWidget；在 `QStyleSheetStyle` 下每个控件都要做 QSS 规则匹配与样式缓存，乘起来占据私有内存的主要部分 |
| 页面事件缓存 | 几十 MB（**峰值时临时叠加**） | `m_eventsMap` 会把当前时间范围跨 bucket 拉下来的 events 以 QJsonArray 全量驻留；只在停留在该页时存在 |
| 服务端数据 | 不计入客户端 | aw-server 是本机独立进程（aws-server 14 MB 级），server/ 下的 sync.db（15 MB）、aw-server.db（4.5 MB）不占客户端内存 |
| 虚拟提交空间 | 5 GB（纸面） | 主要是 D2D1/D3D11 与 CRT 的地址空间预留，物理内存未背页，与看到的 200 MB 无关 |

### 3. 结论要点

- 你的两个最初怀疑（数据字符串 / 渐变主题）**都不成立**——它们加起来不到 3 MB。
- 真实大头是 **界面控件 + 样式系统的固定成本**，以及停留在重页时**页面事件缓存**的临时叠加。
- 「200 MB」里相当一部分是**共享的 Qt + 系统库代码**（工作集口径），真正属于应用的私有内存约 115 MB，峰值时页面缓存再临时加几十 MB。

## 三、针对性优化方案（已实施）

> 按结论直接把「一次性 eager 构造全部页面」改为「只常驻常用的，罕见页用才建、走就放」。

### 页面分级

- **常驻（不回收）**：收件箱 / 任务 / 设置 / 同步。
  - 同步必须常驻：后台心跳、局域网发现、配对托盘气泡都依赖它。
- **可淘汰（懒建 + 离开即销毁 + LRU 有界缓存）**：活动容器、专注容器。

### 三种手段合一

1. **懒建（Lazy）**：启动只构造常驻页；活动/专注的子页面首次点入才 `new` 并挂入 `.ui` 宿主布局。
2. **离开即销毁**：从活动/专注切走时，把整个子页面 widget 树 `deleteLater` 回收（比「只清数据」更进一步，控件本身也被释放）。
3. **LRU 有界缓存**：维护最近使用顺序，超过存活上限（`m_evictableCap`，默认 1）就淘汰最久未用者，恒不淘汰当前页 / 常驻页。

### 状态保留

离开前把当前子标签存进 `m_savedSubtab`，重建后 `setCurrentIndex` 还原——再打开仍是上次看的视图。

### 预期效果

平时待在收件箱 / 任务时，活动与专注容器**零驻留**；即便偶尔看一眼，切走即彻底回收。私有内存从峰值数百 MB 级降到以「常驻页 + 最近一个分析容器」为界，底本明显回落。

## 四、验证方式

- 编译：`just build`
- 部署启动：`just deploy-workshop`（版本 +1，写入 c:/workshop）
- 内存核对：任务管理器观察工作集，切换进活动/专注看上升、切回收件箱看是否回落。

## 五、池化复用的隐性契约（踩坑记录）

卡片池（`CardPool` / `TodoPool`）把「每次渲染 new 一个 widget」换成「回收 + `setNote`/`setTask` 重绑」，
省掉构造、markdown 解析与阴影创建，但顺带抽掉了「widget 与数据一一对应」这个前提，两类问题会跟着来：

1. **信号接线只在创建时挂一次。** 旧写法在 `makeCard()` 里 new 完就连信号；池化后卡片跨重建复用，
   同样的代码放进渲染循环就变成「复用的卡片每次渲染多连一遍」。收件箱这边曾在迁移中把整段接线删掉，
   导致 ⋯ 菜单（转待办/删除/编辑/置顶/详情/评论）、正文 `#标签` 点击、勾选框、多选点选**全部静默失效**
   —— 信号有人 emit、无人 connect，Qt 不会报错。
   现约定：`CardPool::setWiring()` 由宿主注入接线闭包，`acquire()` 只在**新建分支**调用；
   `TodoPage::TodoPool::acquire()` 同构（连接挂在新建的行上）。
   排查口诀：卡片点了没反应 → 先 `grep "&NoteCard::"` 看有没有 connect 侧，别先怀疑数据。
2. **重绑必须清干净上一任的状态。** 曾出现 `setTask` 按下标取容器却把 `m_title` 删掉（启动即崩），
   `setNote` 也会重置 `m_parentRef`、需按 `commentParentId` 重建引用预览。
   卡片上新增任何可视元素，都要在 `setNote`/`setTask` 里交代「重绑时它怎么变」。
