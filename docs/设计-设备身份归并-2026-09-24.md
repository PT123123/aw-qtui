# 设备身份：一机一指纹与旧记录归并

## 1. 要解决什么

mDNS 只回答「怎么互相找到」，不回答「谁是谁」。列表乱的根因是身份模型：

- `device_id` 是 `<data_dir>/device_id` 里的随机 UUIDv4。卸载重装、清除应用数据、换签名键
  （debug↔release）都会换值。
- `devices.id` 是主键 ⇒ **只有 id 变才会多出一行**（换 IP 不会，升级版本也不会）。
- `device_secrets.device_id` 也是主键 ⇒ id 一换，配对密钥就静默失效，得重新配对，
  于是列表里既多一行、又少一层加密。

所以用户看到的「一次升级多一台设备」不是显示 bug，而是数据模型如实记录了两个互不相干的
安装实例。改造前三件事叠在一起把列表搞乱：id 换值、未配对行永不淘汰、`is_online` 恒真（§4）。

本轮的口径：**认得出来 + 摆到眼前 + 由人点一下**。不引入任何自动折叠。

## 2. machine_uid：装机指纹

新模块 `aw-sync-rust/src/machine_uid.rs`。从 OS 级稳定值派生，与安装实例无关：

| 平台 | 原始值 | 备注 |
| --- | --- | --- |
| Windows | `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` | 必须带 `KEY_WOW64_64KEY`：32 位进程会被重定向到 `WOW6432Node`，那里是个复制品，同机派生出两个指纹 |
| Linux | `/etc/machine-id`，退 `/var/lib/dbus/machine-id` | 容器里常只有前者 |
| Android | Kotlin 读 `Settings.Secure.ANDROID_ID` 后经 JNI 注入 | `RustInterface.applySyncMachineUid` → `setSyncMachineUid` → `set_machine_uid_raw("android", raw)`；ANDROID_ID 只有 Java 侧读得到，而派生算法只留一份，所以注入的是**原始值+平台标签** |

派生：`hex(sha256("aw-muid/1\n<platform>\n<raw>"))` 取前 16 个 hex（64 bit）。前缀带版本号，
换口径时新旧必然不同而不是撞在一起。读不到稳定标识就返回 `None`，宁可退回「按 device_id 各算一台」。

### 两条纪律（写在类型与调用点上，不靠自觉）

1. **它不是凭据。** 那些 OS 值本机任何进程都能读、能仿冒。它只驱动「UI 提示这两行疑似同一台
   机器」与归并后的历史归因，**不参与密钥信任，也不省掉配对时的安全码比对**。
2. **它不能被动播出去。** 那是跨网络可跟踪的机器标识。UDP 宣告报文与 mDNS TXT 一律抹掉
   （`discovery::announce_payload` 显式 `machine_uid = None`），`/devices`、`/info` 也不序列化它。
   它只出现在用户主动发起的配对握手报文里（请求与响应两侧），落库后仅用于本机比较。

已知会退化（都往「多一行」退，不会错并）：恢复出厂、Android 工作资料、换签名键。
已知假阳性：**同一台物理机上跑两个独立实例 ⇒ 指纹完全相同**。这是「必须人点确认」的直接理由，
测试台架本身就是这种情形。

## 3. 数据层

全部用 `storage.rs::migrate` 的 `ensure_column` 补列，老库无需迁移脚本：

- `devices.machine_uid TEXT`（+ `idx_devices_muid` 索引，归并候选要按它查）
- `devices.superseded_by TEXT`（非空 = 这一行已归并进别处）
- `device_id_alias(old_id, new_id, merged_at)`

**归并绝不改写主键、绝不删行。** 已同步进来的数据按 `device_id` 归因，删旧行就把历史打掉了。
所以：

| 动作 | 结果 |
| --- | --- |
| 旧行 | 打 `superseded_by = 新 id`、`is_online = 0`，行保留 |
| 新行 | `alias`/`machine_uid` 空则取旧行的，`paired = MAX(两边)`，`paired_at = MIN(两边)`，`last_sync_at` 空则取旧行的 |
| 旧行密钥 | `DELETE FROM device_secrets WHERE device_id = 旧` —— 那个 id 已不再可达，留着只会让人以为还在加密同步 |
| 列表查询 | `get_devices()` 只出 `superseded_by IS NULL` 的行，旧行自然消失 |
| 历史归因 | `resolve_device_id()` 沿 `device_id_alias` 追（最多 8 跳防环），旧 id 仍能解析出设备名 |

方向固定为 **from = 旧（死）id，to = 新（活）id**。反过来会让历史挂 in 一条再也连不上的记录上，
所以服务端与两端 UI 都按这个方向写死，`merge_rejects_anything_that_would_break_attribution` 钉住它。

`merge_device` 的拒绝条件：`from == to`、任一侧是本机、任一侧已被归并过、两边都没配对。

## 4. 顺手修掉的两个列表污染

这两条不是新特性，是让「列表一堆乱码」变轻的既有缺陷：

1. **`is_online` 恒真。** 曾写成字符串比较
   `last_seen_at > datetime('now','-30 seconds')`。SQLite 给出的是 `'2026-09-24 03:00:00'`（空格分隔），
   我们的列存 RFC3339 `'2026-09-24T03:00:00+00:00'`，而 `'T'(0x54) > ' '(0x20)`，
   于是那层「30 秒宽限」判断永远为真 —— 一行只要在线过一次就永远显示在线。
   改为新增 `last_seen_epoch INTEGER`（unix 秒），判定用整数比较（`ONLINE_GRACE_SECS = 30`）。
   这一条做过**反向验证**：把 SQL 临时改回旧写法，回归用例确实失败并报出预期文案，再改回来。
2. **未配对行永不淘汰。** `purge_discovered()`：静默超过 `DISCOVERED_MAX_AGE_DAYS = 7` 天即删，
   再按 LRU 截到 `DISCOVERED_KEEP = 50` 条。作用域严格限定
   `paired = 0 AND is_self = 0 AND seen_via IS NOT NULL` —— 手工登记与配对行永不受影响。
   `purge_stale_paired(days)` 另删「N 天没同步成功过」的配对行，`last_sync_at` 为空的不动。

## 5. 归并提示：挂在哪、什么时候出现

`SyncManager::merge_candidate_for(peer_id)` 产出候选，`GET /devices` 以
`merge_candidate` 字段挂在**命中那一行**上（只含 `id`/`name`/`alias`/`uid_hint`/`paired_at`/
`last_sync_at`/`since_paired_days`；`uid_hint` 只有前 8 个 hex，因为 `/devices` 同网段任何人可读）。

命中时刻有两种：① 对方带着指纹请求配对（接受之前就能提示）；② 列表里已经躺着两行同指纹。
两条防噪规则：

- 提示只挂在**配对较晚**的那一行（`me.paired_at <= old.paired_at` 直接返回 `None`），
  否则两行互指、界面上冒出两个合并按钮，而用户要做的决定其实只有一个。
- 候选选择 `find_merge_candidate` 用 `ORDER BY paired_at ASC LIMIT 1`，两行同指纹时
  稳定指向最早那条。
- 无指纹的行（未配对、纯被发现）在查库之前就返回 `None`，不给每行轮询白加一次索引查询。

握手响应侧曾是缺口：`self_device_info()` 的 `machine_uid` 恒为 `None`，四条配对路径里有三条
永远存不下指纹。现在 `/join`、`/pair/request`、`/pair/confirm` 的响应统一走
`with_outgoing_secret(&self_device_info())` 补齐。

## 6. 两端 UI：提示 + 确认，不自动折叠

同一套语义两份实现，都遵守「默认焦点落在不动数据那一侧」：

| 端 | 位置 | 呈现 |
| --- | --- | --- |
| Android | `SyncRowsAdapter.PairedVH` + `item_sync_device_paired.xml` 的 `mergeRow` | 设备卡里一条琥珀色提示行 + 「归并」按钮；`SyncFragment.onMerge` 弹 `MaterialAlertDialogBuilder`，默认焦点在「保持两台，不合并」 |
| Qt | `SyncPage::renderDevices` 操作列 + `onMergeDevice` | 状态列后缀「· 疑似重装」，操作列「归并」按钮（tooltip 写清旧记录名与指纹片段），`QMessageBox` 默认按钮 `No` |

对话框文案一致地说清四件事：判定依据（同指纹 + 片段值）、旧记录会消失、历史数据归到当前行、
**安全码仍需与对端屏幕核对**。同机双实例的假阳性只能靠这句话兜住。

「一键清理过期设备」（温和版）也一并落到两端：Android 设置面板「配对数据」区、Qt「更多」菜单，
都走 `POST /devices/purge`，确认文案说明两类清理各自的口径。与「清空所有配对信息」（不可恢复）
并排但语义分开。

模型侧：`SyncModels.kt` 加 `Device.mergeCandidate` + `MergeCandidate`；`models.h` 加
`SyncMergeHint` + `SyncDevice::mergeHint`（缺字段时 `toObject()` 给空对象，`id` 空即无效）。
两端都**不**序列化 `machine_uid`，`reinstall_offers_an_explicit_merge_but_changes_nothing_by_itself`
直接断言 `/devices` 与 `/info` 的原始 JSON 文本里不含该字段与完整指纹串。

## 7. 端点

| 端点 | 语义 |
| --- | --- |
| `GET /devices` | 命中时多一个 `merge_candidate` 对象；不序列化 `machine_uid` |
| `POST /merge` `{from,to}` | 归并；成功回 `{ok,merged_from,merged_into}`，并写一条配对类同步日志（否则用户只会问「我的设备怎么不见了」） |
| `POST /devices/purge` `{stale_days}` | 一键清理；回 `{ok,discovered_removed,paired_removed}` |

这两个端点是「用户点一下」才触发的，所以失败也带回话：走 `run_verbose` 而非 `run`，
拒绝回 `400 + {"error":"..."}`（如「找不到设备 x」「这一行已被归并过」），内部故障回
`500 + {"error":"同步管理器暂不可用，请重试"}`。`run` 只能回裸 `Status`，两端 toast 会统一
显示成「服务器错误 (500)」—— 用户看完不知道刚才那一下到底成没成，归并这种动显示结果的
操作尤其不能这样。其余端点维持 `run`，不为了这个把 30 多个 handler 全改一遍。

两端各自负责把那个字段解出来：Android `SyncRepository.httpErrorMessage` 早就会读
`error`/`message`；Qt `ApiClient::parseReply` 原先把整个响应体原样拼在「(HTTP 400): {...}」后面，
现在同样先试 JSON、取出那句话单独展示，取不到才退回带状态码的原始格式。

## 8. 验证

| 命令 | 结果 |
| --- | --- |
| `cargo test -p aw-sync-rust` | 63 通过 / 1 忽略（40 lib + 10 `device_identity` + 5 e2e + 8 pairing；忽略项是真组播用例，见 mDNS 文 §8） |
| `cargo check -p aw-server` | exit 0，仅既有警告 |
| `just kotlinc`（aw-android-native） | BUILD SUCCESSFUL |
| `just build`（aw-qtui） | 23/23 编译并链接通过 |

拒绝原因也真机验过一次：临时起一份 release `aw-server.exe`（端口 5799、`--dbpath` 指到
`%TEMP%` 下的独立库，不碰用户数据），`POST /sync/merge` 传不存在的 id 拿到
`400 {"error":"找不到设备 nope-old"}`，缺字段拿到 `400 {"error":"需要 from 与 to 两个设备 id"}`。

新测试文件 `tests/device_identity.rs` 的 10 条覆盖：在线判定跟随真实时间（而非字符串序）、
发现行按 TTL/LRU 淘汰但配对与手工行不动、**广播报文不含密钥与指纹**、被动路径写不进指纹、
提示只指向已配孪生行且只出现一次、未配对孪生行不是归并目标、归并作废死 id 但保留历史与密钥、
归并拒绝一切会破坏归因的输入、一键清理只丢静默配对。

台架隔离是同一条链上的必要条件：`tests/sync_e2e_http.rs` 用私有 UDP 端口（47611，而非真实
服务的 46000）+ `discovery_method = "udp_only"`，`mdns_discovery.rs` 标 `#[ignore]`。
否则测试进程注册的 `_aw-sync._tcp` 会被真实 `aw-server.exe` 收到、写进用户的信任列表。

## 9. 本轮顺带修掉的真 bug

`paircode.rs::join_with_code` 原样入库了加入方报文里的 `is_self`。那个字段是「对方眼中的自己」，
恒为 `true` —— 于是刚配好的这台在码主列表里被标成本机，前端 `!isSelf` 一过滤就整机消失
（「配了个寂寞」）。现在强制 `device.is_self = false`。这条是新用例
`reinstall_offers_an_explicit_merge_but_changes_nothing_by_itself` 逼出来的：它断言配对后
两台都还在列表里，实际拿到 0 台。

## 10. 未做 / 待办

- **同机双实例不做自动判定**：目前只能靠用户看出「这两行其实是一台」。要真区分需要实例级
  标识（如 data_dir 指纹），本轮没有引入。
- **`device_secrets` 不迁移**：归并只作废旧 id 的密钥，新 id 想继续加密同步得重新走一次握手。
  提示文案里说了，但没有做「归并即换绑」。
- **归并不可撤销**：没有 `unmerge`。旧行数据仍在库里（只打 `superseded_by`），
  真要撤销手动清掉那个字段即可，但没有端点与界面。
- 两端未做「批量归并」：一次只处理一对候选。
- 待真机手测：Windows 平板重装后，桌面端能否看到「疑似重装」提示并完成归并；
  归并后旧行是否真的不再出现在两端列表里。
- 待办（与本轮无关）：`aw-qtui` 的死 mDNS 模块退役；`.quarantine-20260924/` 由用户删除。
